Generalities

Goal

To give developers a guide for an easy and quick integration with the services Pagadito
offers with technologies which is compatible.

Audience

Software Developers, Integration Leads, Project Managers, IT Managers.

Summary

This is a Guide of Integration with each of the services Pagadito offers to Developers
and Merchants. You have a description of each service, steps how it works, an
integration diagram between your website with Pagadito and example codes for each
technology with Pagadito is compatible.
With this guide you will understand how each service works and get an easy and quick
integration of your website with Pagadito, both its testing platform SandBox and its live
environment.

SandBox

Pagadito has a testing platform for you to make all the tests you need during the
integration of your website, app or system with Pagadito. You can go clicking on the link
https://sandbox.pagadito.com/.

Contact

In any doubt, please contact us to our email developers@pagadito.com.

Payment with Tokenization

Description

Consist in processing payments for a Merchant without redirection, where Merchant
requests to the user his credit/debit card information and send it to Pagadito. Additional
to the charge, Pagadito generates a token associated with the credit/debit card, to send
future charges using only this token instead of all the credit/debit card information. This
service does not require the user to be redirected to a payment screen, that is why your
website or app is in charge of the complete payment process. Communication with
Pagadito is through an API REST.

Use

This is a variant of the payment without redirection, ideal for websites or apps that
receive payments with credit/debit cards which already request this information and
makes charges to the credit/debit without asking the information again.

Steps

    1. User arrives to your website, picks products or services to buy and enters his
         credit/debit card information.

    2. Your website sends to Pagadito the information of the payment.
    3. Pagadito processes the payment.
    4. Pagadito return the information of the payment including the token associated

         with the credit/debit card.
    5. Your website shows a confirmation page.

Payment with Tokenized Card

Description

Consists in processing payments for a Merchant without redirection, using the token
associated with a credit/debit card processed and tokenized previously. This service
does not require the user to be redirected to a payment screen, that's why your website
or app is in charge of the complete payment process. Communication with Pagadito is
through an API REST.

Use

Ideal for websites or apps that makes charges to the credit/debit card of the user
without requiring he enters the information again. With this service, your website or app
will be able to send new charges without being the user present nor he has to enter his
credit/debit card information again, because when the initial charge is processed, an
identifier is generated to be reused.

Steps

    1. User arrives to your website, picks products or services to buy and enters his
         credit/debit card information.

    2. Your website send to Pagadito the information of the payment including the token
         associated with the card.

    3. Pagadito processes the payment.
    4. Pagadito return the information of the payment including the token associated

         with the credit/debit card.
    5. Your website shows a confirmation page.

Subscription with Tokenization

Description

It consists of the processing of payments and scheduling of collections to futures for a
Trade without redirection, the merchant asks the user for the data of his Credit / Debit
Card and sends them to Pagadito. In addition to the charge to the card, Pagadito
generates a token associated with the card, to make future charges using only this
token instead of all the card data. This service does not require the user to be redirected
to a payment screen, so your website or app is responsible for the entire payment
process. Communication with Pagadito is through a REST API.

Use

Ideal for websites or applications that offer subscriptions with defined packages, that is,
the user knows the number of payments that will be charged to his account on a
periodic basis. With this service, your website or application must request the user's
credit/debit card information only once, and the card will be charged on the defined dates.

Steps

    1. The user arrives at your website, chooses the products or services to pay and
         enters the details of his credit / debit card.

    2. Tu sitio web envía a Pagadito los datos del pago.
    3. Pagadito processes the payment.
    4. Pagadito returns payment information including subscription code and

         credit/debit card token.
    5. Your website or app shows a confirmation screen.

Tokenized Card Subscription

Description

It consists of the processing of payments andscheduling of collections to futures for a
Commerce without redirection, using the token of a credit / debit card previously
processed and tokenized. This service does not require the user to be redirected to a
payment screen, so your website or app is responsible for the entire payment process.
Communication with Pagadito is through a REST API.

Use

Ideal for websites or apps that offer scalable subscriptions or renewal of a completed
subscription. With this service, your website or application will be able to send new
charges without the need for the user to be present or for them to re-enter their
credit/debit card details.

Steps

    1. The user arrives at your website, chooses the products or services to pay and
         enters the details of his credit / debit card.

    2. Your website sends Pagadito payment details.
    3. Pagadito processes the payment.
    4. Pagadito returns payment information including subscription code and

         credit/debit card token.
    5. Your website or app shows a confirmation screen.

Webhooks

Description

Webhooks are HTTP callbacks that receive notifications for the event types which are
configured. They are asynchronous, the order is not guaranteed and when they are sent
more than one time the result does not change.

Use

Ideal for websites or apps that need an asynchronous confirmation when the status of a
transaction change. With this service, your website or app will not be without knowing
the last status per each transaction.

Configuration

From section Technical Configuration -> Webhooks, you have to add the listener URL
and save the configuration.

Events

They are notifications that are sent to the configured URL, when a trigger is activated,
for example the change of status of a payment. When an event occurs, Pagadito
notifies through a POST HTTP request, which contains the details of the event and the
information of the transaction.

Types
The types of events are the different triggers that activate the sending of a notification.
The supported types of events in this moment are the following:

     TRANSACTION.STATUS.CHANGE: This event is triggered when a payment is
         registered. Also when it changes its status to completed, verifying, revoked or
         expired.

                                                                                                                             39
Information
When an event occurred, Pagadito sends the notification of the event in format JSON
encode. If the website or app is not available or it takes too long to answer (timeout),
Pagadito cancels the request and tries again until a maximum of 20 times during the
following 3 days. The parameter event_type indicates the trigger of the event.

Signature
Each one of the sent messages are signed. It is important to verify that:

     The Webhook event was originated from Pagadito.
     The Webhook event was not modified during its transmission.
     The Webhook event goes to the right receiver.

The following headers are used to give information for validation of the signature.

     PAGADITO-SIGNATURE: asymmetric signature generated by Pagadito Base64
         encoded.

     PAGADITO-AUTH-ALGO: algorithm used to generate and validate the
         asymmetric signature.

     PAGADITO-CERT-URL: URL address to download the certificate of public key
         X509 to be used in the verification process.

The signature is generated through the concatenation of five values, using | (vertical
line) as separator.:

     Notification ID: Unique identifier of the HTTP notification. It is contained in the
         header PAGADITO-NOTIFICATION-ID.

     Timestamp Notification: Timestamp of the HTTP notification. It is contained in the
         header PAGADITO-NOTIFICATION-TIMESTAMP.

     Event ID: Identifier of the event. It is included in the event's body.
     Cyclic Redundancy Check (CRC32): Checksum CRC32 for the body of the HTTP

         request.
     WSK: Connection credential of the Merchant Account.

The input string to validate the signature would have the following shape:

                   NotificationId|TimestampNotification|EventIdD|CRC32|WSK

The authentication algorithm specified in PAGADITO-AUTH-ALGO uses an asymmetric
signature algorithm. This allows to Pagadito to use a private key to create the signature

                                                                                                                             41
in PAGADITO-SIGNATURE, and allows you to use a public key contained in the
certificate which source is defined in PAGADITO-CERT-URL to verify the Webhook
event.

Code

Read and verify webhook
To validate the webhook notification you have to get the headers of the notification, the
certificate and to validate the signature of the message.
[ PHP ]

<?php
       /* Get headers */
       $headers = getallheaders();
       $notification_id = $headers['PAGADITO-NOTIFICATION-ID'];
       $notification_timestamp = $headers['PAGADITO-NOTIFICATION-TIMESTAMP'];
       $auth_algo = $headers['PAGADITO-AUTH-ALGO'];
       $cert_url = $headers['PAGADITO-CERT-URL'];
       $notification_signature = base64_decode($headers['PAGADITO-SIGNATURE']);

       /* Get data */
       $data = file_get_contents('php://input');

       /* Get Event ID */
       $array_data = json_decode($data, TRUE);
       $event_id = $array_data['id'];

       /* Copy from Technical Configuration -> Integration Parameters */
       $wsk = 'SET-YOUR-WSK';

       /* Generate validation string */
       $data_signed = $notification_id . '|' . $notification_timestamp . '|' .
$event_id . '|' . crc32($data) . '|' . $wsk;

       /* Get content of certificate */
       $http_options = array(

              'http' => array(
                     'protocol_version' => '1.1',
                     'method' => 'GET',
                     'header' => array(

                                                                                                                             42
                             'Connection: close'
                     ),
              )
       );
       $cert_stream_context = stream_context_create($http_options);
       $cert_content = file_get_contents($cert_url, FALSE,
$cert_stream_context);

       /* Get public key */
       $pubkeyid = openssl_pkey_get_public($cert_content);

       /* Verify sign */
       $verification = openssl_verify($data_signed, $notification_signature,
$pubkeyid, $auth_algo);

       /* Free public key */
       openssl_free_key($pubkeyid);

       /* Validation */
       if ($verification == 1) {

              die(`Valid');
       } elseif ($verification == 0) {

              die(`Invalid');
       } else {

              die(`Error');
       }
?>
